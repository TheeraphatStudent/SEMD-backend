# SEMD Backend — Refactor Roadmap

Sequences the migration from current state (`SEMD_BACKEND_CURRENT_STATE.md`) to target architecture (`SEMD_BACKEND_TARGET_ARCHITECTURE.md`). Complexity uses XS/S/M/L/XL, not hours, per the mandate. This is a planning document — no code changes here. Phases 4-6 are scoped but not started; each requires its own checkpoint before beginning per the mandate's "complete and validate one feature before moving to the next" rule.

## Phase 4 — Feature-by-feature refactoring

Order follows the mandate's default (dependency-driven: Authentication first, since every other feature depends on `AuthGuard`). Each feature is only started after the previous one passes its acceptance gate. Full per-feature detail (files, API/DB impact, migration notes, rollback, tests) is produced **at the start of that feature's own work**, not speculatively here — per the mandate's own phasing rule ("do not begin production-code refactoring before completing Phases 0-2," and by extension, don't over-specify Phase 4 details that depend on what Phase 3 actually lands as). This roadmap fixes the **order and the known concrete findings** each feature must address, based on the current-state audit.

| Order | Feature | Known concrete findings to address (from current-state audit) | Complexity | Depends on |
|---|---|---|---|---|
| 1 | Authentication & Identity | TOTP secret plaintext storage; OAuth `state` not verified on callback; unused `PyJWT` dependency; refresh-token rotation/revocation not yet proven (needs characterization tests before touching) | L | Phase 3 error handling + security core |
| 2 | Users, Roles, Permissions | Role stored as plain string (no DB enum) — decide whether to add a Postgres enum or keep app-level validation; build the permission matrix (not yet documented anywhere) | M | Feature 1 |
| 3 | API Access Keys | Already reasonably solid (hashed at rest, shown-once) — mainly needs typed-error migration + tests | S | Feature 1 |
| 4 | Browser Extension Access Codes | **Plaintext storage** (unlike access keys) and **low entropy** (6 chars, ~35.7 bits) with **no rate limiting** — concrete security fix, not just refactor | M | Feature 1, Phase 3 rate-limiting decision (not yet scoped — see Phase 3 open item below) |
| 5 | URL Evaluation (Prediction) | No SSRF/scheme validation before dispatch (Phase 3 `core/security.py` gets wired in here); blocking `time.sleep` poll in `MLServiceClient` (event-loop-blocking); `Any`-typed response fields | L | Phase 3 security core, Feature 1 |
| 6 | Third-Party Detection Services | Not deeply audited in Phase 1 — needs its own current-flow trace before target-flow design (config-driven executor is reasonable but under-tested) | M | Feature 5 |
| 7 | URL Reports | Not deeply audited in Phase 1 beyond confirming routes exist and work — needs state-diagram verification against actual `url_report`/`url_reported` status transitions in code | M | Feature 5 |
| 8 | URL Flags & Whitelist Rules | Precedence between user flag / global whitelist / global blacklist / model / third-party result **not documented anywhere in code or docs today** — must be reverse-engineered from `control/` logic and made explicit, or decided fresh if genuinely undefined | M | Feature 5, 7 |
| 9 | Dashboard & Statistics | **32 of 32 endpoints are stub `pass` handlers returning nothing, unauthenticated, and broken** (fail Pydantic response validation on every call) — this is closer to greenfield implementation than refactoring; needs a product decision on real requirements before design | XL | Features 1, 5, 7, 8 (aggregates their data) |
| 10 | ML Model Registry & Prediction (registry metadata only — no in-process inference exists) | Metadata CRUD is reasonable; orphaned unauthenticated `MLTrainingRouter` needs a decision (wire up with auth, or delete) | M | Feature 5 |
| 11 | Dataset & Retraining Management | `services/queue_service.py` exists but not deeply audited — needs current-flow trace | M | Feature 10 |
| 12 | Background Workers & Redis | `workers/prediction_worker.py`'s stale-client import fixed in Phase 3; job-payload versioning (mandate requirement) not yet implemented — add during this feature, not before, to avoid touching worker code twice | S (given Phase 3 already fixes the import) | Phase 3 |
| 13 | System & Audit Logs | `activity_log` table exists; whether it's actually populated on every relevant action (auth events, role changes, key/code creation, report decisions, flag changes, model activation) was **not verified** in Phase 1 — needs a coverage check against the mandate's required audit-event list before calling this "working" | M | All above (each feature's audit-logging coverage is checked as part of that feature, plus a final sweep here) |

**Open item carried from Phase 3 into Feature 4's dependency**: rate limiting has no home yet in the target architecture — needs a decision (in-process, e.g. `slowapi`, vs. reverse-proxy/gateway-level) before Feature 4 (Extension Access Codes) and Feature 1 (login/TOTP brute-force protection) can be called complete. Recommend deciding this at the start of Feature 1, since Feature 1 needs it as much as Feature 4 does.

## Phase 5 — Cross-feature integration validation

Scoped once Phase 4 features complete; not detailed here per the same reasoning as Phase 4's per-feature detail. Will re-run the full endpoint inventory, full OpenAPI diff (`openapi.before.json` vs. `openapi.after.json`, classified compatible/additive/deprecated/breaking/accidental), and cross-feature smoke tests (e.g., a URL flagged by one user doesn't leak into another user's evaluation result).

## Phase 6 — Final documentation and handoff

Produces `SEMD_BACKEND_FINAL_HANDOFF.md` per the mandate's deliverable list, once Phase 5 passes.

## What this roadmap deliberately does not do yet

- Does not fabricate per-feature file lists for Features 6-13 — those depend on code not yet re-read in feature-scoped depth (the current-state audit was necessarily broad, not exhaustive per domain).
- Does not commit to Alembic vs. continued raw-SQL-init schema management — flagged as a decision needed before Phase 3's DB item, not decided here (see target architecture §5).
- Does not decide the Dashboard/Stats rebuild's actual requirements (Feature 9) — that's a product question, not an engineering one; engineering can only flag that today's implementation is 100% non-functional stubs.
